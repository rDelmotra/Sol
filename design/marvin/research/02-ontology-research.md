## Summary (what to take away)

1. **Adopt patterns, not artifacts.** The only openly licensed, well-maintained pieces are BFO (ISO/IEC 21838-2:2021, CC BY 4.0), CCO (BSD-3), SOSA/SSN, OWL-Time, GeoSPARQL, MF-JSON, STIX, CCSDS messages. Rovetto's space ontologies are all-rights-reserved with no OWL file in the repos; CUBRC's Space Domain Ontologies (BFO+CCO-based, the real successor) have public papers but I found no public OWL. Matheus/Kokar's STO OWL URL returns 404.
2. **The best single template for "every feed writes a record" is `sosa:Observation`** (`madeBySensor`, `observedProperty`, `hasFeatureOfInterest`, `hasResult`, `phenomenonTime`, `resultTime`), plus one thing no standard provides: our own `recordedAt` (transaction time). SOSA's two times are both world-side.
3. **The best template for time-varying values is Matheus et al. 2003:** a value is valid from the event that set it to the event that superseded it (`PropertyValue` with `startEvent`/`endEvent`, `value`, `certainty`), and model-driven values (position from velocity) are a `DynamicSystem`. This equals "present = fold over the log" plus our SGP4 live plane.
4. **The best template for situations is Kokar et al. 2009 (STO) + the CCSDS Conjunction Data Message:** reify the situation as an object with its own id, participants, attributes, interval, producer and creation time; register "standing" situations because you cannot materialise all relations (SAWA lesson).
5. **Palantir's lasting contributions:** object types + interfaces (polymorphic questions across entity kinds), actions as the only write path with an action log, time series as keyed side-series. Its object store is current-state, not log-derived.
6. **Space data in practice** (USSF UDL via its public SDK, CCSDS ODM/CDM) is a flat catalog of record types with explicit frame/time-system fields and a current/history split - not an ontology. The explicit per-record `REF_FRAME`/`TIME_SYSTEM` is the thing the semantic standards lack.
7. **Biggest gaps (section 11):** inertial/dynamic frames in a queryable model; storing model-derived state as a function with validity/uncertainty; cross-source supersession policy; situation lifecycle and pushed deltas at scale; an LLM-targeted query IR with typed refusals.

## 1. Matheus, Kokar & Baclawski - Core Ontology for Situation Awareness (FUSION 2003); SAWA; Information Fusion 2009

**Verified citations** (PDFs read in full text via local extraction):
- C. J. Matheus, M. M. Kokar, K. Baclawski, "A Core Ontology for Situation Awareness," Proc. 6th Int. Conf. on Information Fusion (FUSION 2003), Cairns, Australia, vol. 1, pp. 545-552. PDF read: https://www.ece.northeastern.edu/fac-ece/kokar/publications/Fusion03.pdf (author copy; venue/pages from citing literature and Baclawski's publication list, https://ken.baclawski.com/pub/index.html - the PDF itself does not print the venue line).
- C. J. Matheus, M. M. Kokar, K. Baclawski, J. A. Letkowski, C. Call, M. L. Hinman, J. J. Salerno, D. M. Boulware, "SAWA: An Assistant for Higher-Level Fusion and Situation Awareness," SPIE vol. 5813, Multisensor, Multisource Information Fusion, 2005, doi 10.1117/12.604120. PDF read: https://ece.northeastern.edu/fac-ece/kokar/publications/SPIE2005.pdf
- M. M. Kokar, C. J. Matheus, K. Baclawski, "Ontology-based situation awareness," Information Fusion 10(1):83-98, 2009, doi 10.1016/j.inffus.2007.01.004 (received Aug 2006, accepted Jan 2007). PDF read: https://ece.northeastern.edu/fac-ece/kokar/publications/INFFUS277.pdf. STO OWL file location as printed in the paper: http://vistology.com/ont/2006/STO/STO.owl - I tried it on 2026-10-19 and got HTTP 404, so **the STO OWL file is not currently retrievable from the URL in the paper** (not located elsewhere; availability unverified, treat as unavailable).

**2003 core SAW ontology (what is actually in the PDF).** It is a UML class diagram (Fig. 1), later published as DAML/OWL. Classes named in the text: `Situation` (a collection of `Goal`s, `SituationObject`s and `Relation`s), `SituationObject` (physical or abstract; has `Attribute`s; participates in relations), `PhysicalObject` (subclass of SituationObject; "necessarily has" the attributes `Volume`, `Position`, `Velocity`), `Attribute`, `Relation` (over ordered sets of SituationObjects; example `inRangeOf(X,Y)`), `PropertyValue`, `EventNotice`, `DynamicSystem`, `Goal`. Paper says it considers only binary relations in the formal definition; extendable to higher arity. The DAML instance example uses `saw:PhysicalObject`, `saw:attribute`, `saw:Position`, `saw:PropertyValue` with `saw:startEvent`, `saw:endEvent`, `saw:value`, `saw:certainty`, and `saw:EventNotice` with `saw:time` (xsd:dateTime) and `saw:eventSource`.

**How time-varying values are modelled - the paper's central, explicitly argued design decision.** Four designs were compared:
1. *Snapshot*: a `Snapshot` class with a unique `time`, holding AttributeValues and Relations that hold at that instant. Rejected: redundant when nothing changes, and assumes all sensors update in lock-step.
2. *TimeInterval*: values and relations each carry aggregations of `TimeInterval` (start, end).
3. *PropertyValue with certainty*: `AttributeValue` generalised to `PropertyValue` so that Attributes and Relations both carry value + certainty (certainty cannot live on the Relation itself without being time-invariant).
4. **Final design: `EventNotice` as interval markers.** A `PropertyValue` has a `startEvent` and `endEvent` (both EventNotices) and defines two time-dependent functions, `value` and `certainty`. A new PropertyValue is created for an Attribute/Relation whenever an EventNotice "affects" it; the next EventNotice implicitly ends the previous PropertyValue. An open interval = no endEvent. The `TimeInterval` class is eliminated. `EventNotice` = a sensor's notification, at a time, from an `eventSource`, that defines/constrains a value. A `PropertyValue` may be implemented as a `DynamicSystem` (value/certainty evolve without new notices, e.g. Position projected from Velocity with growing uncertainty).

Reading for OrbitWatch: this is, in 2003, an event-sourced + valid-time model: observation records (EventNotice) are the log; "present" is derived by finding the PropertyValue in effect at time t; predicted values (SGP4) are a DynamicSystem. That is our log + live plane in other words. Weakness: valid-time interval is *implicit* in event arrival, so there is no separate record of "when we learned it" vs "when it was true" (see section 8).

**Relations and situations (2003).** A `Relation` is an ordered tuple of SituationObjects whose truth value over time is also a PropertyValue stream (value + certainty, start/end events). A `Situation` is just a container (objects + relations + goal); it is not itself time-bounded and not reified with its own attributes. `Goal` is the "standing relation" of interest (SAWA calls it that).

**SAWA (2005): what changed.** Tooling paper, not a new ontology. The core is simplified to `Situation` = Objects + Relations + Goal (standing relation); `Objects` have `AttributeTuple`s (Attribute + collection of `AttributeValue`s defined by `ExternalEvent`s); `Relations` are realised through `RelationTuple`s connecting pairs of Objects with `RelationValue`s "defined by the firing of Rules". Genuinely new: (a) a separate **Event Ontology** (Fig. 6: each Event describes one or more Objects, each Attribute with a value and a certainty), known only to an Event Management Component so other event ontologies can be plugged in; (b) OWL + SWRL rules derive relations from level-1 events, with a Relation Monitoring Agent (Jess/Rete) that fires only for the user's "standing relations"; (c) a triples DB keeps "a historical record of all situation events". Reason for change: the number of possible relations is unbounded, so you monitor only the relations a user declared interest in. Maturity: research prototype (SBIR, AFRL-funded).

**Information Fusion 2009 (Situation Theory Ontology, STO).** Rebuilt the core on Barwise/Devlin situation theory. Classes: `Situation` (subclasses `UtteranceSituation`, `ResourceSituation`, `FocalSituation`), `Individual`, `RelevantIndividual`, `Relation` (n-ary), `ElementaryInfon`, `Rule`, `Attribute` (with subclasses `Location` and `Time`), `Dimensionality`, `Polarity` (two instances, 1 and 0). Properties: `relevantIndividual` (inverse `inSituation`), `relevantRelation`, `focalIndividual` (sub-property of relevantIndividual), `focalRelation`, `hasAttribute` (domain includes Situation, so **situations are first-class objects with their own attributes**), `hasAttributeValue`, `focalSituation`/`utteranceSituation`, `resourceSituation`/`referringSituation`. The old `Goal` is explicitly renamed: "In our SAW Core Ontology [4] we used to call this class Goal" - it becomes the *utterance situation* (the query). Time handling: `Time` and `Location` become ordinary Attribute subtypes, and an infon (R, a1..an, polarity) can carry them as slots - "the time when the property holds". The 2003 `PropertyValue`/`EventNotice` machinery does not appear in the 2009 paper (I searched the extracted text for both terms). Why it changed: to capture Barwise's situation semantics ("situations as first-class citizens", "supports" vs "derives") with a commonly supported language, and to treat a *query* as an utterance situation - which matches our LLM-asks-question design.

**Fit for OrbitWatch: adopt the pattern, not the OWL files.** Take: (i) value-with-validity-interval, closed by the *next observation*, plus a predictive "dynamic system" value that is explicitly flagged as model-derived; (ii) Relations as time-bounded, certainty-carrying facts; (iii) the idea that a Situation is a reified object with its own attributes, and a *standing* situation is a registered interest ("standing relation"; this equals our resident-set/standing IR program); (iv) the SAWA lesson that you cannot materialise all relations, only declared ones. Skip: the OWL/DAML artifacts (2003-era, DAML, Jess), n-ary-infon/polarity machinery, `Goal`.

### 2b. The real successor: CUBRC / U. Buffalo Space Object Ontology -> Common Core Space Domain Ontologies (BFO + CCO based)
- A. P. Cox, C. K. Nebelecky, R. Rudnicki, W. A. Tagliaferri, J. L. Crassidis, B. Smith, "The Space Object Ontology," 19th Int. Conf. on Information Fusion (FUSION 2016), Heidelberg, 5-8 July 2016, pp. 146-153 (venue/pages verified via search metadata: Semantic Scholar, PhilArchive record https://philarchive.org/rec/COXTSO-9, researchr listing of FUSION 2016). Full text read: https://ancs.eng.buffalo.edu/pdf/ancs_papers/2016/Fusion2016_SOO_paper_Final_v2.1.pdf . Funded by AFRL (contract FA8750-13-C-0236, printed in the PDF). Venue/year are from search result + author affiliations; the PDF text does not print the conference name (treat venue line as "per search metadata").
- Follow-up: Cox et al., "An Overview of the Common Core Space Domain Ontologies," 15 Feb 2019, "draft version for public release" (https://philarchive.org/archive/COXTSD-2; I could not retrieve it - HTTP 403 - so module list is from a secondary source). Per the CCO paper's reference list and an NCOR wiki page (https://ncorwiki.buffalo.edu/index.php/Ontologies_of_Space_and_Ground_Systems), the Space Domain Ontologies (SDO) are modules: Outer Space, Space Event, Space Object, Spacecraft, Spacecraft Mission (+ Sensor, Agent, Cyber elsewhere). 
- **Modelling choices (from the FUSION 2016 text):** built on BFO (upper) and CCO (mid), >700 classes. "Space Object" is deliberately a *defined class* - `object and (located_in some 'Region of Outer Space')` - because it is a *phase sortal* (a spacecraft is only a space object while in outer space). Subtypes: `Central Body` (bears a central-body role), `Resident Space Object` (orbits another space object), `Space Debris Object`, `Orbital Debris Object` (man-made only), `Artificial RSO`, `Natural RSO`, `Near Earth Object`. `Spacecraft` is NOT a subtype of Space Object; `Satellite Artifact` is a Spacecraft designed to remain in orbit. **Orbit is a process** (subtype of `Spaceflight`); `Orbital Path` is a 3-D spatial region; `Orbital Revolution` is a fiat process part. Orbital elements are *qualities* (inclination = relational quality between orbital plane and reference plane); mean motion, delta-v are measurements of *process profiles*. Orbital classes (GEO etc.) are *defined classes inferred by a reasoner*, to avoid asserted multiple parentage. Time/space: "Every process occurs at a given spatial region and occurs on a given temporal region"; data are time-stamped through their connection with processes; coordinate system = subtype of Descriptive Information Content Entity. Also: plans (`Spacecraft Mission Plan` as a Directive ICE) versus what actually happened (patterns of life; anomaly = deviation). Integration claim: TLE, ephemeris, maneuver data, and the UCS Satellite Database were mapped into one RDF triple store and queried with SPARQL (their example queries: "all spacecraft in LEO with inclination > 60 that can communicate on Ku or C band").
- **Availability:** CCO is public: https://github.com/CommonCoreOntology/CommonCoreOntologies, BSD-3-Clause, .ttl files, "eleven ontologies" (Jensen et al., "The Common Core Ontologies," FOIS 2024, arXiv:2404.17758 - read). I found NO public OWL release of the Space Domain Ontologies; documentation is public, the artifacts may not be (unverified - needs a repo check by a human).
- **Fit:** adopt the *modelling decisions*, not the files. Concretely: identity of a physical object is separate from its phase (in-orbit / decayed / on-pad); orbit is a process, not a property; orbital elements are time-stamped measurements belonging to a process or observation; plan vs actual are separate things; classes like GEO/LEO are *derived* classes, not stored (matches our derived-from-state regime fields). Do not adopt OWL/DL reasoning for 33k objects at 1 Hz; the paper itself only demonstrates SPARQL over a triple store.

## 3. BFO (ISO/IEC 21838-2:2021) and DoD/IC Common Core Ontologies

**Standard.** ISO/IEC 21838-2:2021, "Information technology - Top-level ontologies (TLO) - Part 2: Basic Formal Ontology (BFO)", published 2021-11, Edition 1, 13 pp. (iso.org/standard/74572.html and webstore.iec.ch/en/publication/72703 via search; the iso.org page itself returned 403 to my fetcher). It standardises BFO-2020 definitions plus OWL 2 and Common Logic axiomatisations. Artifacts: https://github.com/BFO-ontology/BFO-2020 , `21838-2/owl/bfo-core.owl|.ttl`, CC BY 4.0 (README).

**The split we need (class names from bfo-core.ttl, read):**
- `continuant` (endures, no temporal parts) -> `independent continuant` (-> `material entity` -> `object`, `object aggregate`, `fiat object part`; `immaterial entity` -> `site`, `spatial region`, `continuant fiat boundary`), `specifically dependent continuant` (-> `quality`, `relational quality`, `realizable entity` -> `role`, `disposition`, `function`), `generically dependent continuant` (information; "may be copied across bearers").
- `occurrent` -> `process`, `process boundary`, `history`, `spatiotemporal region`, `temporal region` (-> `temporal instant`, `temporal interval`).
- Relations (with IDs, from the TTL): `exists at` BFO_0000108 (entity -> temporal region), `occupies temporal region` 0000199, `occupies spatial region` 0000210, `occupies spatiotemporal region` 0000200, `has participant` 0000057 / `participates in` 0000056, `occurs in` 0000066, `bearer of` 0000196 / `inheres in` 0000197, `has temporal part` 0000121, `precedes` 0000063, `located in` 0000171, `realizes` 0000055, `concretizes` 0000059, `has first instant` / `has last instant`.
- **Time handling - the part to be careful about:** BFO-2020's OWL has *no* time-indexed (temporally qualified) versions of its continuant relations. The time parameter is only implicit in the prose definitions ("at t"), with `exists at` the one explicit link. The TTL scope notes tell users who need it to import a temporal extension. (Read from the tool's summary of the TTL; the final ~9k characters were not read.) So: **BFO tells you what kind of thing a "value that changes" is (a quality of a continuant, whose changes are processes/events), but it does not give you a way to store "quality q had value v during [t1,t2]" in OWL.** Every BFO-based system re-invents this (CCO does it by reifying measurement/information content entities with time stamps).

**DoD/IC adoption - what is verified.** University at Buffalo news release, 28 Feb 2024 (https://www.buffalo.edu/news/releases/2024/02/department-of-defense-ontology.html, read): the chief data officers of DoD, ODNI, and CDAO agreed (about Jan 2024) that BFO and CCO are the "baseline standards for formal DOD and IC ontology"; John Beverley is quoted that the agreement "directs agencies to use open-source standards" for data integration. The release gives no compliance deadline or enforcement mechanism, and I did not retrieve the memo itself (secondary: https://dailynous.com/2024/03/07/department-of-defense-adopts-a-philosophers-applied-ontology/). CCO is independently reported to be under IEEE P3195 review as a mid-level ontology standard (Jensen et al., FOIS 2024) and "widely used in defense and intelligence" - self-reported by CCO authors. **Implication for OrbitWatch:** if the product ever has to interoperate with US government space data, BFO/CCO-aligned *names* are the lingua franca; the practical cost of aligning is a mapping table, not a rewrite. Nobody mandates BFO for a JSON event log.

**Fit: adopt the pattern (continuant/occurrent, quality-vs-role, phase sortal, process occurs-at region/time), do not adopt OWL/BFO as runtime machinery.** Two specific things to copy: (1) *roles* (central-body role, operator role, "active"/"inactive" operational status as role/phase, not intrinsic type) - this fits the existing "inactive_satellite" categorical field badly; (2) *information content vs the thing it is about* (a TLE/OMM is an information entity about an orbit, not the orbit).

## 4. W3C SOSA/SSN (the best fit for "every feed writes an observation")

**Status (verified).** "Semantic Sensor Network Ontology," W3C Recommendation 19 Oct 2017 (OGC 16-079), editors Haller, Janowicz, Cox, Le Phuoc, Taylor, Lefrancois, https://www.w3.org/TR/vocab-ssn/ . Journal paper: Janowicz, Haller, Cox, Le Phuoc, Lefrancois, "SOSA: A Lightweight Ontology for Sensors, Observations, Samples, and Actuators," Journal of Web Semantics (2018/2019; doi 10.1016/j.websem.2018.06.003; arXiv:1805.09979). A "2023 Edition" (https://www.w3.org/TR/vocab-ssn-2023/, OGC 25-022) is a *Working Draft* as of the page I fetched; it adds a canonical RDF implementation of OMS (the Observations, Measurements and Samples model; I take this to be ISO 19156, edition year not verified in the text I read) as a "SOSA-OMS" module (includes `sosa-oms:validTime`), an SSN-SAREF alignment, and deprecates `ObservableProperty`/`ActuatableProperty` specialisations of `ssn:Property`; backward compatibility is claimed. Treat 2017 as the stable Rec and 2023 as moving. SOSA is self-contained and imports no other ontology; full SSN is the heavier layer (and SOSA drops the earlier DUL alignment, offered only as an optional non-normative module). Licence: W3C/OGC document licence (copyright OGC+W3C; the spec text gave no separate licence line).

**Exact terms we would use.**
- `sosa:Observation` - "Act of carrying out an (Observation) Procedure to estimate or calculate a value of a property of a FeatureOfInterest." An *act*, i.e. an occurrent: it has a time and a provenance. Properties: `sosa:madeBySensor` (inverse `madeObservation`), `sosa:observedProperty`, `sosa:hasFeatureOfInterest`, `sosa:hasResult`, `sosa:hasSimpleResult`, `sosa:usedProcedure`, `sosa:phenomenonTime`, `sosa:resultTime`.
- `sosa:Sensor` (subclass of `ssn:System`; carried by a `sosa:Platform`, `sosa:hosts`/`isHostedBy`), `sosa:FeatureOfInterest` ("the thing whose property is being estimated"), `sosa:ObservableProperty` ("an observable quality ... of a FeatureOfInterest"; subclass of `ssn:Property`), `sosa:Result`, `sosa:Procedure`.
- `sosa:Sample` ("Feature which is intended to be representative of a FeatureOfInterest"), `sosa:Sampling`, `sosa:isSampleOf`/`hasSample`. For us a *Sample* maps to a derived or sub-selected view (e.g., "the visible-pass subset", a constellation, an orbit shell as a representative of "LEO") - interesting but optional.
- Also `sosa:Actuation`/`Actuator` (the "writes back" side; relevant to our Action concept).
- **Time, defined exactly:** `sosa:phenomenonTime` = "The time that the Result of an Observation ... applies to the FeatureOfInterest"; may differ from `resultTime`, can be an instant, an interval, or another compound temporal entity. `sosa:resultTime` = the instant the activity was completed (xsd:dateTime). So SOSA gives you *valid time* (phenomenonTime) and *event/production time* (resultTime) for free; it does **not** define a third "when did the store learn this" (transaction time) - that is ours to add (section 8). `sosa-oms:validTime` in the 2023 draft (OMS: the period in which the result may be used) is a fourth, "freshness window" notion.

**What it does NOT do.** SOSA models an observation, not the "current value". There is no "state of a Feature at time t" construct, no retraction/supersession, no derived-event class, and `Result` is deliberately opaque (could be a number, a TLE/OMM record, or an image). Observed value is on the Observation; the property is on the Feature - so *the current value of a property is a query over Observations*. That is exactly our "present is computed from the log".

**Used in production?** Unverified. I did not look for or confirm any named production deployment of SOSA/SSN (IoT or otherwise), and I found no space-domain deployment; do not claim one. What is verified is only that it is a joint W3C/OGC Recommendation (2017) with a 2023 edition in the standards pipeline. Also unresolved: one search summary said the 2023 draft deprecates `sosa:Result`, but the fetched spec text I read did not confirm that (it listed `hasResult` normally and only mentioned deprecation of the `ObservableProperty`/`ActuatableProperty` specialisations) - treat any change to `Result` as unverified and check the change log (Annex G.1) before relying on it.

**Fit: ADOPT the pattern and the names for the Observation record.** Every feed (Space-Track GP fetch, SWPC Kp, Horizons vector, METAR, a conjunction message) becomes: Observation {id, madeBySensor/Source, observedProperty, featureOfInterest, hasResult/hasSimpleResult, phenomenonTime, resultTime, usedProcedure}. Do not import the OWL files or full SSN.

## 5. W3C Time Ontology in OWL (OWL-Time)

**Status (verified).** Original W3C Recommendation 19 Oct 2017; 2020 Candidate Recommendation (26 Mar 2020) and a Candidate Recommendation Draft dated 15 Nov 2022 are the current /TR/owl-time/ page (editors Simon Cox, Chris Little; original Hobbs & Pan). https://www.w3.org/TR/owl-time/ . Interest-Group Notes on extensions (entity relations, temporal aggregates) were published 7 Jul 2020 and are not expected to become Recs.

**Minimal subset we need** (exact names):
- `time:TemporalEntity` = `time:Instant` (zero extent) | `time:Interval`; `time:ProperInterval` (non-zero extent; subclass of Interval; disjoint from Instant).
- `time:hasBeginning`, `time:hasEnd` (Interval -> Instant); `time:inXSDDateTimeStamp` (Instant -> xsd:dateTimeStamp); `time:inside` (Interval -> Instant, endpoints excluded); `time:before`/`time:after` (TemporalEntity).
- Allen relations between `time:ProperInterval`s: `time:intervalBefore/After`, `intervalMeets/MetBy`, `intervalOverlaps/OverlappedBy`, `intervalStarts/StartedBy`, `intervalDuring/Contains`, `intervalFinishes/FinishedBy`, `intervalEquals`; convenience unions `time:intervalDisjoint` (= before or after) and `time:intervalIn` (= during, starts, finishes).
- `time:hasTime` attaches a TemporalEntity to any thing, but the WG says it exists "only for users who cannot or will not define their own predicates" (i.e. do not rely on it).
- Not needed: `time:TemporalPosition/TimePosition/TRS`, calendar descriptions, durations (though TRS matters if we ever need TAI/UTC/TT distinctions - orbital-core time work already handles that).

**Fit: adopt the vocabulary of interval relations, not RDF.** Situations hold over `[hasBeginning, hasEnd]`; closed-open intervals with an unbounded end for "still holds". Ship Allen's 13 relations as query operators named exactly as above (`intervalOverlaps`, `intervalDuring`, `intervalMeets`...). Note OWL-Time's "instant is zero-extent" vs a half-open interval convention: pick one (recommend half-open `[start, end)`) and document it; OWL-Time does not impose either.

## 6. OGC GeoSPARQL 1.1 and OGC Moving Features

**GeoSPARQL 1.1** - OGC 22-047r1, "OGC GeoSPARQL - A Geographic Query Language for RDF Data," published 2024-01-29 per the front matter (the page's "approved" date field read inconsistently, so I treat approval date as unverified). https://docs.ogc.org/is/22-047r1/22-047r1.html . Reusable by name:
- `geo:SpatialObject` ("Anything spatial (being or having a shape, position or an extent)") > `geo:Feature` ("A discrete spatial phenomenon in a universe of discourse") and `geo:Geometry` (Feature and Geometry are disjoint); `geo:hasGeometry`, `geo:hasDefaultGeometry`; serialisations `geo:asWKT`, `geo:asGeoJSON`, `geo:asGML`, `geo:hasSerialization`; 1.1 adds `geo:hasMetricArea`, `geo:hasCentroid`, `geo:asDGGS`.
- Topology vocabulary in three families: Simple Features (`geo:sfEquals`, `sfDisjoint`, `sfIntersects`, `sfTouches`, `sfCrosses`, `sfWithin`, `sfContains`, `sfOverlaps`), Egenhofer (`eh*`) and RCC8 (`rcc8*`) - family names from the conformance table and search summary; I did not confirm every `eh`/`rcc8` property IRI.
- **Time:** the spec states it "does not directly provide support for temporality" and points to OWL-Time for temporal predicates; spatio-temporal query extensions are not part of the standard. It lists an informative BFO alignment annex (E.16), content not read.
- **Gaps for us:** the geometry model is Simple Features geometries (WKT/GML/GeoJSON/DGGS serialisations) in a spatial reference system (my reading; default CRS84 per OGC convention - not confirmed in the text I read); there is no ECI/inertial frame, no moving frame (Earth rotates under TEME), no notion of "above region Y at altitude h". 
- **Fit: adopt names for the *relations*** (`within`, `intersects`, `contains`, `overlaps`, `disjoint`, `touches`) on Feature/Geometry pairs and the Feature-vs-Geometry split; skip the RDF/WKT stack. Our "over region" is a time-varying relation computed from the propagated sub-satellite point, which GeoSPARQL cannot express.

**OGC Moving Features** - the relevant encoding is MF-JSON: "OGC Moving Features Encoding Extension - JSON," OGC 19-045r3, v1.0, approved 2020-02-22, published 2020-06-02 (front matter read), based on a subset of ISO 19141:2008, "inspired by" GeoJSON RFC 7946. https://docs.ogc.org/is/19-045r3/19-045r3.html . Related: OGC API - Moving Features Part 1: Core (OGC 22-003r3). Members (spec mirror at https://ksookim.github.io/mf-json/ read, plus search summary of the official doc; the official page body beyond the intro was not retrievable by my tool, so treat member-level detail as second-hand): a `MovingFeature` is a GeoJSON-like `"Feature"` with mandatory `temporalGeometry`, and optional `temporalProperties`, `time` (a `LifeSpan`), `bbox`, `geometry`, `properties`, `id`, plus defaults `crs` (`urn:ogc:def:crs:OGC:1.3:CRS84`) and `trs` (`urn:ogc:data:time:iso8601`). `temporalGeometry` = {`type`: `MovingPoint`|`MovingLineString`|`MovingPolygon`|`MovingPointCloud`, `datetimes`, `coordinates`, `interpolation` (`Discrete`|`Step`|`Linear`|`Quadratic`|`Cubic`|URL; default `Linear`), `base`, `orientations`, `crs`, `trs`}. `temporalProperties` = {`datetimes`, one or more `@propertyN` each with `type`/`values`/optional `interpolation` (`Discrete`|`Step`|`Linear`|`Regression`|TimeseriesML URL)/`form`/`description`}. Key idea: **a time-varying property is a parallel (datetimes, values, interpolation) array**, and the interpolation *rule* is part of the data.
- **Fit: adopt the pattern, not the format.** Matches how we already store SGP4 ephemeris (state vectors + interpolation) and Horizons DSO samples (Hermite). The explicit `interpolation` and `trs` members are worth copying as metadata on any time-series property. Limitation: CRS84 is Earth-fixed lon/lat; an `crs` member could name TEME but nothing in the standard defines it (frame handling is ours; see sections 9 and 11).

## 7. Palantir Foundry Ontology (production system; public docs only)

Sources read: https://www.palantir.com/docs/foundry/architecture-center/ontology-system , /docs/foundry/ontologies/ontologies-overview , /docs/foundry/object-backend/overview , /docs/foundry/interfaces/interface-overview , /docs/foundry/time-series/* (via search summaries of time-series-properties and time-series-syncs), /docs/foundry/action-types/action-log (via search summary). This is vendor documentation: it describes what exists in a commercial product, not a standard. It is the strongest "used in production" evidence in this report for the *shape* of a many-entity operational model.

- **Resources in an ontology:** object types, link types, action types, interfaces, shared properties, object type groups (ontologies-overview). An object type = display name + typed properties + primary key + backing dataset(s) (third-party explainers; the Ontology Manager overview lists metadata, properties, action types, link type graph, dependents, data, usage). Link types connect two object types with cardinality; one-to-many via foreign key, many-to-many via a join dataset.
- **Semantic vs kinetic:** "Data objects are the semantic nouns, and actions are the kinetic verbs" (architecture center). Semantic = objects, properties, links, (interfaces); kinetic = action types, functions, dynamic security. Palantir explicitly says the Ontology is *not* a "semantic layer" because data, logic, action and security must be integrated. Architecture: *Language* (defines objects/links/properties/actions/automations/logic), *Engine* (reads: queries, real-time subscriptions to state changes, materialisations; writes: atomic durable transactions, batch, streams, CDC), *Toolchain* (Ontology SDK).
- **Backend:** Ontology Metadata Service, object databases (Object Storage v1 "Phonograph" is legacy and, per the page, was scheduled to be unavailable after 2026-06-30 - that date has now passed, current status unverified; v2 is canonical), Object Set Service (reads: search/filter/aggregate; static and dynamic object sets that "re-evaluate their filters as new data arrives"), **Object Data Funnel** (writes datasets/streams into the ontology and indexes), **Actions service** (applies user edits under permissions/conditions; up to 10,000 objects per action). Data enters via two paths - source data through Funnel, user edits through Actions - and the docs do not say how conflicts between the two are resolved (unverified; flag for design).
- **Action types:** a defined set of changes to objects, property values and links, executed atomically with side effects (notifications, permission checks). Each action type can emit an **action log**: one new "[LOG]" object per submission, auto-linked to every object edited, storing action RID, action type version, user ID and timestamp by default. Docs distinguish *action log* (decisions as ontology data) from *edit history* (every edit to an object type). So audit-by-event exists, but it is a **log of user actions**, not a general append-only fact log: the object store holds current state.
- **Interfaces:** abstract types describing a *shape* (interface properties, link type constraints, action type constraints). Cannot be instantiated; object types implement one or many; interfaces can extend interfaces; Object Set Service can search/sort by interface (polymorphic queries), but aggregation by interface and interface link types were "in development" and action constraints in beta, SDK TypeScript-only (as read). **This is the right answer to "many entity kinds sharing a few fields (position, frame, owner)" - copy it.**
- **Time-varying data:** handled by a *separate mechanism*: a **time series property** (TSP) on an object type, whose value is a string *series ID*; a **time series sync** (dataset or stream) supplies rows `seriesId (string), timestamp (timestamp|long), value (double|int|float|string)`, optional ingestion-time column; TSP cannot be the primary key or title property; multiple syncs per TSP require Object Storage v2. I.e. Foundry's object properties are *current state* and anything that evolves is a keyed side-series. Note the optional ingestion-time column: even Palantir has an event-time + ingestion-time pair, though not a bitemporal model. Time-series interpolation is documented as a separate page (not read).
- **Not documented / not found:** a first-class "event" or "situation" object (people model these as ordinary object types - e.g. an "Alert" or "Flight Delay" object linked to others); any valid-time/transaction-time model for object properties; geospatial frame handling (not examined).

**Fit: adopt the pattern.** (1) Object types + typed properties + link types with cardinality as the *registry* (our field registry already is the property half). (2) **Interfaces** as the way to let one question span debris, rocket bodies, spacecraft, ground stations, regions (all implement `Locatable`, `Named`, `HasOperator`...). (3) **Action types as the only write path with a log of every action**, kept separate from the semantic layer. (4) Time series as keyed side-series, not as objects. Skip: Foundry's dataset-backed indexing, ontology manager UI, current-state-only object store (we want present = f(log)).

Honest caveat: everything above is vendor-authored documentation; I did not find independent evaluations in this pass, and claims about scale/latency are marketing-adjacent and not used here.

## 8. Event sourcing and bitemporal modelling

**Sources (verified).**
- R. T. Snodgrass, *Developing Time-Oriented Database Applications in SQL*, Morgan Kaufmann, July 1999, ISBN 1-55860-436-7; free PDF from the author: https://www2.cs.arizona.edu/~rts/tdbbook.pdf . Definitions (from the book as summarised by the search result; not re-read in full): **valid time** = when a fact is true in the modelled reality; **transaction time** = when a fact is stored in the database; the two are orthogonal; a table with both is *bitemporal*; chapters 6-7 define current / sequenced / non-sequenced queries and modifications; ch. 8-10 cover transaction-time and bitemporal tables. (Fowler attributes the terms "valid time" and "transaction time" to Snodgrass; I did not trace their earlier origin.)
- K. G. Kulkarni & J.-E. Michels, "Temporal features in SQL:2011," SIGMOD Record 41(3):34-43, Sept 2012, doi 10.1145/2380776.2380786, https://sigmodrecord.org/publications/sigmodRecord/1209/pdfs/07.industry.kulkarni.pdf . SQL:2011 does not add a period *type*; it adds *period definitions* as table metadata over a pair of datetime columns. **Application-time period** (user-named; = valid time) and **system-versioned tables / `SYSTEM_TIME` period** (fixed name; = transaction time); a table can have both = bitemporal. Standard: ISO/IEC 9075-2:2011 (standard text not read; I rely on this paper by two of its authors).
- M. Fowler, "Bitemporal History," 7 Apr 2021, https://martinfowler.com/articles/bitemporal-history.html (read). He renames the pair: **actual time** (= valid/effective) and **record time** (= transaction), "when we learned about a fact"; queries take two dates (`salaryAt(actualDate, recordDate)`); generalises record time to "perspectives" (different observers' views, or hypothetical scenarios); models it either as bitemporal ranges or as *bitemporal events in event sourcing*.
- M. Fowler, "Event Sourcing," 12 Dec 2005, https://martinfowler.com/eaaDev/EventSourcing.html (read; marked as draft he no longer maintains): store every change as an ordered sequence of events; current state derives from the log; past states can be reconstructed; retroactive/out-of-order events are handled by reversing and replaying; snapshots are periodic caches that can be rebuilt in parallel. His example event stores both an occurrence time and a recorded time.
- M. Kleppmann, *Designing Data-Intensive Applications*, O'Reilly, March 2017 (1st ed.), ch. 11 "Stream Processing" > "Databases and Streams" > Change Data Capture / Event Sourcing / "State, Streams, and Immutability" (location confirmed from the O'Reilly TOC; I could not retrieve the chapter text, so I make no claims about its exact arguments beyond: the log is the source of truth, derived state is a cache that can be recomputed). A 2nd edition (Kleppmann & Riccomini) exists. Treat as "unverified detail".

**Mapping to SOSA (the question asked).**

| Concept | Snodgrass / SQL:2011 | Fowler 2021 | SOSA | Orbital example |
|---|---|---|---|---|
| When it was true / what time the result applies to | valid time / application-time period | actual time | `sosa:phenomenonTime` (instant or interval) | TLE/OMM **EPOCH**; a Kp index's 3-hour window; a launch's liftoff instant |
| When the measurement/activity finished | (no direct column) | (not separate) | `sosa:resultTime` | when Space-Track's GP generation finished / sensor tracklet end |
| When our system learned/stored it | transaction time / `SYSTEM_TIME` | record time | **none** (OMS 2023 draft adds only `validTime` = usability window) | log append time (`recorded_at`) |

So SOSA's two times are **both "world-side"** (what the data is about, and when the producer made it). Neither is the store's transaction time. A correct log needs all three: `phenomenonTime`, `resultTime`, `recordedAt` (+ optionally a usability window from OMS `validTime`). Only the third is needed for "what did the system believe at time T" / reproducible answers / late corrections; the first is needed for "what was true at t". For orbital data this matters concretely: an element set has an epoch (phenomenon), a producer creation time where the message carries one (CCSDS ODM headers carry `CREATION_DATE`; whether the Space-Track GP payload exposes an equivalent is not checked here) (result), and our ingest time (record), and the *propagated position at t* is a derived value that depends on which element set was chosen - so a replayable answer needs the record-time cut-off.

**Standards disagree on terminology only; the structure is the same.** Recommend Snodgrass/SQL:2011 words in storage (`valid_*`, `recorded_*`/`system_*`) because they are standardised (I did not check what Postgres/Timescale support natively), SOSA words on the Observation record because that is the sensor vocabulary, and not Fowler's "actual/record" (he says he switched to those words because readers found valid/transaction time confusing; they are the same concepts).

**Fit: adopt the pattern in full.** Event log = append-only, immutable entries carrying the three times; corrections are new entries that *supersede* (`supersedes: id`), never edits; "present" = a fold over entries with `recordedAt <= now`, state at (valid t, record r) = fold with both cuts; snapshots/checkpoints are caches. What none of these give you: a compact rule for *what supersedes what* across different sources of the same property (see section 11).

## 9. Other precedents

- **JDL / DFIG (the level model that defines "situation").** Steinberg, Bowman & White, "Revisions to the JDL data fusion model," Proc. SPIE 3719, pp. 430-441, 1999 (cited in the FUSION 2003 paper, which quotes it): Level 2 = "estimation and prediction of relations among entities"; Level 1 = entities; Level 3 = impact; Level 4 = process refinement. Blasch, Steinberg, Das, Llinas, Chong, Kessler, Waltz & White, "Revisiting the JDL model for information exploitation," Proc. 16th Int. Conf. on Information Fusion, 2013, pp. 129-136 (DFIG; https://apps.dtic.mil/sti/pdfs/ADA619203.pdf): L0 features, L1 entities, L2 structures (relationships and situations), L3 scenarios/outcomes, L4 the system itself; DFIG adds L5 user refinement and L6 mission management. **Proposed framework, not an implementation.** Use: the vocabulary "entity -> relation -> situation -> impact", and the rule that L2 products are *derived* from L1 tracks. Kokar/Matheus (section 1) is the only formalisation I found that makes L2 relations first-class objects.
- **NATO JC3IEDM (STANAG 5525; MIP).** A ratified (STANAG 5525) C2 information-exchange data model used by MIP nations (deployment scale not verified): IDEF1X entity-relationship model with, per the MIP/Wikipedia/DTIC summaries, 271 entities, 1,460 attributes, 233 relationships. Root entities `OBJECT-ITEM`, `CONTEXT`, `ACTION`, `ADDRESS`, `AFFILIATION`; `REPORTING-DATA` ("source and timing that apply to reported data"), `HOLDING` (what an object has "at a particular time"), `CONTEXT-ELEMENT-STATUS`. Requirement stated in the MIP overview: represent current, past and future roles of objects in plans, orders and events. I did not retrieve the spec's exact valid-time attribute names (unverified). Successor MIP Information Model (MIM) is being proposed as STANAG 5643. **Use: a ratified precedent for "object-item + reporting-data (who said it, when) + action/event" in C2 exchange. Pattern: every statement carries its reporter.** Heavyweight relational model; do not adopt tables.
- **CCSDS Navigation Data Messages (the space-ops entity schemas).** *Orbit Data Messages* CCSDS 502.0-B-3 (April 2023; https://ccsds.org/Pubs/502x0b3e1.pdf): OPM, OMM (mean elements; the repo's provider payloads are OMM-shaped per 01-code-inventory, not independently checked here), OEM, OCM. Header keywords `CREATION_DATE`, `ORIGINATOR`; metadata `CENTER_NAME` (frame origin; EARTH, MOON, ...), `REF_FRAME` (e.g. EME2000, ITRF-xx, TEME), `TIME_SYSTEM` (UTC, TAI, TT, GPS, TDB). *Conjunction Data Message* CCSDS 508.0-B-1 (https://ccsds.org/Pubs/508x0b1e2c2.pdf): header `CREATION_DATE`, `ORIGINATOR`, `MESSAGE_ID`; relative data `TCA`, `MISS_DISTANCE` (m); two object blocks `OBJECT1`/`OBJECT2` with `OBJECT_DESIGNATOR`, `CATALOG_NAME`, `INTERNATIONAL_DESIGNATOR`, `OBJECT_TYPE`, `REF_FRAME`, state vector and covariance. The US Office of Space Commerce's TraCSS publishes profiles of these (CDM, OMM, OCM specs; found via search results, space.commerce.gov), which shows operational use by at least that system; adoption by other operators is not verified here. The CDM is the best existing *template for a situation*: a typed relation between two entities, with an event time (TCA), a producer (`ORIGINATOR`), a creation time and message id, frame, and numeric attributes - and it is a message (observation of a derived event), not a state. Frame and time-system are explicit *per message* (this is the thing BFO, GeoSPARQL and SOSA do not give us).
- **USSF Unified Data Library (UDL).** Public, access-controlled REST API; I read Bluestaq's open-source Python SDK (Apache-2.0) `api.md` (https://github.com/Bluestaq/udl-python-sdk, 5,572 lines, treated as data), which lists the resource model, not field schemas. Findings: **167 top-level resource types** (e.g. `Elsets`, `StateVector`, `Ephemeris`, `Conjunctions`, `Maneuvers`, `Onorbit`, `Onorbitevent`, `LaunchEvent`, `LaunchSite`, `Sensor`, `Site`, `Organization`, `Observations`, `SpaceEnvObservation`, `WeatherData`, `Airfields`, `EventEvolution`), each exposing uniform verbs (`create`, `create_bulk`, `retrieve`, `list`, `count`, `queryhelp`, `tuple`, file-drop publish); **69 have a `History` sub-resource and 2 (`Elsets`, `StateVector`) also a `Current` sub-resource** - i.e. the production space-data library separates "current view" from "history" per record type. A Kratos article (kratosspace.com) says UDL holds "over 4000 different types" of data and that most common SDA types are observations, element sets, state vectors and ephemeris; GAO reported (2023) that operators were not using it in daily SSA operations because it was not integrated into their operational systems (via Via Satellite/Breaking Defense summaries, not read in primary). **Use: confirms the "flat catalog of record types + uniform verbs + current/history" shape is what the actual space-data world looks like. It has no ontology, no situation type, no frames model (unverified below the resource level).**
- **STIX 2.1 (OASIS Standard, 10 June 2021).** Cyber-threat JSON object model used widely in intel sharing: domain objects (SDOs) and relationship objects (SROs: `Relationship`, `Sighting`); common properties `id`, `created`, `modified`, `revoked`; **a version is identified by `id` + `modified`**, only the creator may version or revoke, revocation is permanent (spec text read). `Sighting` carries `first_seen`/`last_seen` (window; per search summary of spec) and `Indicator` has `valid_from`/`valid_until`; I could not confirm `Relationship.start_time/stop_time` in the text I read (unverified). **Use: the cleanest JSON precedent for "entity + typed link with its own validity window + immutable versions + sighting-as-observation-of-entity".** Domain is wrong (cyber), shape is right.
- **NASA/NAIF SPICE frames.** https://naif.jpl.nasa.gov/pub/naif/toolkit_docs/C/req/frames.html (read): a frame is a *named, integer-identified* set of axes with a class (inertial built-in e.g. J2000/ECLIPJ2000; PCK body-fixed e.g. IAU_EARTH, ITRF93; CK-based; fixed-offset TK; dynamic; switch); transforms (`sxform`/`pxform`) are functions of epoch. **Use: the right model for a `Frame` entity: named, id'd, transformable at a time, with a declared class.** Not an ontology; a computation library. (As far as I read, GeoSPARQL and MF-JSON carry a CRS identifier but define no inertial or dynamic frames.)
- **Descriptions & Situations (DOLCE+DnS Ultralite).** Gangemi & Mika, "Understanding the Semantic Web through Descriptions and Situations," CoopIS/DOA/ODBASE 2003, LNCS 2888 (pages differ between sources). A `Situation` is a reified state of affairs that `satisfies` a `Description`; entities in it are linked by `isSettingFor`. Included because it is the main *academic* alternative to Barwise/STO for reifying situations (BFO-2020's class list has no situation class). Research-grade; used in many linked-data projects, not an operational standard.
- **Allen interval algebra.** J. F. Allen, "Maintaining knowledge about temporal intervals," CACM 26(11):832-843, 1983, doi 10.1145/182.358434: the 13 relations; OWL-Time's interval properties map one-to-one onto them (mapping table in the OWL-Time spec, section 5).
- **Other, not evaluated in depth:** NASA MSFC "Common Space Systems Ontology" (Johnson, Thomas, Diaz, IEEE AeroConf 2023; BFO+CCO-based, early version, for concept-stage modelling) - relevant mostly as another data point (my judgement) that BFO+CCO is where the space-ontology work is converging; I only read its abstract.

## 10. Proposed MINIMAL CORE VOCABULARY

Design rule: *every term must be justified by a standard term or by a gap flagged in section 11.* 14 concepts. Names in `code` are the exact terms in the cited standard; where we deliberately differ, "ours".

| # | Concept | What it is (one line) | Borrowed from (exact term) |
|---|---|---|---|
| 1 | **Entity** | A thing with a stable id that outlives its property values (satellite, debris piece, launch, organisation, ground station, region, storm). | `sosa:FeatureOfInterest` (what is observed); `geo:Feature`; BFO `continuant` / `independent continuant`; JC3IEDM `OBJECT-ITEM`; Foundry "object". Name ours: `Entity`. |
| 2 | **EntityType** (+ **Interface**) | Registry of kinds, each with a typed property list and links; interfaces are abstract shapes several types implement (`Locatable`, `HasOperator`). | Foundry `object type` + `interface` (adopt); existing `FIELD_REGISTRY`. BFO `class`/CCO subclasses only as naming guidance. |
| 3 | **Property** (definition) | A named, typed, unit-bearing, frame-aware attribute of an EntityType; says *how* its value varies (static / piecewise-in-time / model-derived). | `sosa:ObservableProperty` / `ssn:Property`; BFO `quality`; MF-JSON `temporalProperties` incl. `interpolation`; Foundry "property", "time series property". |
| 4 | **Value** (property at an interval) | One value of a Property of an Entity over a valid-time interval, with source and certainty; closed by the next value from that source. | Matheus 2003 `PropertyValue` {`value`, `certainty`, `startEvent`, `endEvent`}; SQL:2011 *application-time period*; OWL-Time `ProperInterval`. Derived/model values flagged as `DynamicSystem`-style (Matheus). |
| 5 | **Relation** (Link) | Typed directed link between two Entities, itself time-bounded, source-attributed and revocable. Cardinality declared on the LinkType. | Matheus `Relation`; Foundry `link type`; STIX `Relationship` (+ own validity); BFO relations (`participates in`, `located in`, `part of`) as the *names* for LinkTypes. |
| 6 | **Observation** | Immutable record that a Source produced a Result about a property of an Entity, with 3 times. THE log record for every feed. | `sosa:Observation`: `madeBySensor`, `observedProperty`, `hasFeatureOfInterest`, `hasResult`/`hasSimpleResult`, `usedProcedure`, `phenomenonTime`, `resultTime`; plus ours `recordedAt` (SQL:2011 `SYSTEM_TIME`; Fowler "record time"). |
| 7 | **Event** | A derived, discrete, named happening about one or more Entities at an instant or short interval (launch, decay, maneuver, storm onset). Produced by rules/detectors from Observations; itself logged. | Matheus `EventNotice` (sensor-side) / BFO `process boundary` & `process`; SSAO terms (`Orbital Collision Event`, `Space Object Detection Event`, `Space Weather Event`) for the names; Space Event Ontology (CUBRC) module name. Ours: `Event` is a *log entry kind*, not a class tree. |
| 8 | **Situation** | A reified relation (or set of relations/values) among Entities that holds over a valid-time interval, derived by a registered rule; has its own id, attributes, participants, and lifecycle (opened/closed/superseded). | Kokar 2009 STO `Situation` (+ `relevantIndividual`, `hasAttribute`, "situations as objects"); DUL `Situation` / `isSettingFor`; JDL L2; CDM as the concrete message shape (TCA, miss distance, originator). Interval vocabulary: OWL-Time Allen relations. |
| 9 | **Source** (Sensor / Procedure) | Who/what produced a record: feed, sensor, algorithm, human, with version and trust metadata. | `sosa:Sensor` + `sosa:Platform` + `sosa:Procedure`; CDM `ORIGINATOR` (SANA registry); JC3IEDM `REPORTING-DATA`; STIX `created_by_ref`. |
| 10 | **Frame** | Named, id'd reference frame/CRS with class, origin, time system; transformable at an epoch. | CCSDS ODM `CENTER_NAME`, `REF_FRAME`, `TIME_SYSTEM` (SANA values); SPICE frame classes; CRS in GeoSPARQL/MF-JSON `crs`/`trs` (names only). Ours: it must include TEME/ECI. |
| 11 | **Region** (+ **Location**) | Spatial extent as an Entity: ground polygon, orbit shell, altitude band, airfield, city; Location = (Frame, coordinates) or a Region reference or none. | `geo:Feature` + `geo:Geometry`/`geo:hasGeometry`; BFO `spatial region`, `site`; SOO `Region of Outer Space`, `Orbital Path`. Topological predicates named per GeoSPARQL `geo:sfWithin`/`sfIntersects`. |
| 12 | **Interval** (time) | Half-open valid-time interval with Allen relations; unbounded end = still holds. | OWL-Time `time:ProperInterval`, `hasBeginning`/`hasEnd`, `intervalDuring`, `intervalOverlaps`, `intervalMeets`...; SQL:2011 period. |
| 13 | **Log entry** (envelope) | Append-only record = {id, kind (Observation | Event | SituationChange | Action | Correction), payload, `supersedes?`, `recordedAt`}. Present = fold over the log. | Fowler "Event Sourcing" (event log), STIX versioning (`id`+`modified`, `revoked`), SQL:2011 system-versioning; Foundry action log. |
| 14 | **Action** | A named, permissioned write/command with parameters and a logged outcome (set a watch, subscribe, mark mission ended). Separate from the semantic layer. | Foundry `action type` + action log; `sosa:Actuation` (name). |

Notes on minimality. Collapse candidates if you want fewer: merge 12 into 4/8 (just intervals), merge 14 into 13 (an Action is a log kind). I recommend keeping Frame, Source and Situation as distinct concepts because they are exactly where ad-hoc models later leak.

**Where standards disagree, with a recommendation.**
1. *Are situations/relations entities?* BFO-2020's class list (as returned from the BFO-2020 repository README and TTL) contains no `situation` class, and BFO's general stance is that relations are not entities (that second point is BFO's documented realist position as I understand it; I did not re-verify it in the ISO text). STO (Kokar 2009: "situations are first-class", verified in the paper), DUL (`Situation`/`isSettingFor`), STIX (`Relationship` is its own object with an id), Foundry (reifies *actions* as `[LOG]` objects and lets you model an alert/delay as an ordinary object type, but a link type itself is not an object), and JDL L2 (relations as the L2 product) reify them. **Reify situations and time-bounded relations** (we must attach intervals, certainty, source, and push subscriptions to them). Keep BFO's naming for the *relations used as LinkTypes*.
2. *Where does time attach?* BFO: implicit "at t" in prose, one explicit `exists at`; OWL-Time/GeoSPARQL: separate predicates; SOSA: on the observation; Matheus/SQL:2011/STIX: on the value or link as an interval. **Attach on the Value/Link/Situation (interval) and on the Observation (phenomenon/result/recorded).**
3. *Property vs observation vs role.* BFO makes "operational status" a `role` or `quality`; SOSA treats the property as fixed and each reading as an Observation; Foundry stores current state. **Store Observations (log), keep a derived current Value, model role-like facts (operator, central body, active/defunct) as time-bounded Relations.**
4. *Two times or three?* SOSA has 2 world-side times; temporal DB literature has valid + transaction; OMS adds usability window. **Use 3 (+ optional usability window).** See section 8.
5. *Orbit: property or process?* SOO (BFO): `Orbit` is a process, `Orbital Path` a region, elements are qualities; SSAO and our registry: `has_orbit`/mean elements are attributes. **Keep elements as Values (derived from OMM Observations) but do not model "orbit" as a stored property of the object; the propagated trajectory is a `DynamicSystem`-style derived value.**
6. *Space Object as a type?* SOO: a *phase* (defined class); catalog (`objectType`): a fixed type. **Phase as a Relation/Value (`orbitalStatus`: in_orbit/decayed with intervals), type from catalog.**
7. *Terminology of time:* SOSA `phenomenonTime`/`resultTime` vs SQL:2011 `application-time`/`SYSTEM_TIME` vs Fowler actual/record. **Use SOSA names on Observations, SQL:2011 names in storage.**

## 11. What none of these solve for OrbitWatch

1. **Inertial and dynamic frames in a semantic model.** GeoSPARQL and MF-JSON are Earth-fixed CRS84-centric; BFO has `spatial region` but no frame transformation; CCSDS/SPICE name frames and time systems but are not queryable ontologies. We need `Frame` + `at(epoch)` transformation as part of the query language, and "over region Y" defined through a time-varying sub-satellite-point relation (TEME -> ECEF -> geodetic), not a stored geometry.
2. **Model-derived, high-rate state.** SOSA/BFO/OWL assume stored observations. Positions of 33,000 objects at 1 Hz are a *function of one Value (the element set) and time* (Matheus's `DynamicSystem` is the only mention among the sources I reviewed). Nothing says how to store the function once, version it, bound its validity (our +/-60 day propagation window), and attach uncertainty that grows with |t - epoch|. This is the central gap.
3. **Supersession rules across competing sources.** Which element set wins at record time r: Space-Track vs CelesTrak vs owner-operator ephemeris? SOSA, Matheus and STIX give you provenance but no precedence/fusion policy; JDL L1 does this in the track-fusion world and is not formalised for catalog data.
4. **Situation lifecycle and incremental maintenance at scale.** Matheus/SAWA argue for "standing relations" only (you cannot materialise all relations); STO and DUL define situations statically. Open: detecting open/close of "A over B", conjunction screening across 33k x 33k, and *pushing deltas* (enter/exit) to subscribed clients with exactly-once, replayable semantics. The nearest existing code is the resident-set diff (`ResidentSet`, per 01-code-inventory); no standard describes subscription semantics over such a model.
5. **A query language that an LLM can target and that cannot compute numbers.** SPARQL (which the SOO paper uses) and GeoSPARQL are the closest standard query languages I reviewed; as far as I read, neither has built-in orbit propagation or inertial-frame transforms, and neither is designed around guarantees for LLM-generated queries (my judgement; their full function libraries were not reviewed). Our IR already exists; none of the standards supply the typed-refusal and "hollow answer" discipline.
6. **Vague/partial dates and uncertain identity.** GCAT's vague dates, 596 un-NORAD'd rows, and inferred (not sourced) program membership (01-code-inventory) need first-class "precision" and "inferred" flags; OWL-Time has a calendar-description mechanism (`time:hasDateTimeDescription` was seen in the spec; I did not read its granularity/unit classes, so how well it expresses "year only" or "month only" is unverified), but none of the standards say anything about inference provenance on links except Matheus `certainty` and STIX `confidence` (STIX `confidence` is listed among its common properties in my search summary; not read in the spec text).
7. **Weather/aurora/storm geometry as moving fields**, not moving points. MF-JSON handles moving features (points/polygons); fields (Kp, gridded density) are coverages - OGC has other standards (not evaluated here) and nothing ties them to the same Entity/Observation model.
8. **Licensing realities.** Rovetto's ontologies are not usable; CUBRC's Space Domain Ontologies' artifacts were not found public; only BFO (CC BY 4.0) and CCO (BSD-3) are clearly open. So adopt *terms and patterns*, cite sources, and keep our own JSON schema.
