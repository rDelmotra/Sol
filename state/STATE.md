As of commit `55ff01d` plus the catalog-fetch and alerts fix on branch `sre/hardening`, 2026-10-18.

## What Orbitwatch is

A browser app that shows every tracked object in Earth orbit in 3D, live.
It also shows deep-space objects (Artemis II) and answers plain-English questions about the sky.
Backend: Express. Frontend: React, three.js, Zustand, Vite. Physics: SGP4.

## Recent milestones (newest first)

- Catalog fetch rules on `sre/hardening` (D14, corrected by D16). (1) At most 5 Space-Track logins per UTC day, counted in `spacetrack-attempts.json` (`attemptDay`, `attemptsToday`, `successToday`, `alertSentDay`, `alertStreakDays`; `packages/backend/src/cache/attempt-log.ts`). Boot, cron and retry-timer attempts all count, success or failure. The wait between attempts is computed from that day's failures: 15 min, 30 min, 1 h, 2 h (the 5th attempt is about 3 h 45 min after the 1st), and it starts again each UTC day, so an outage gets all 5 attempts every day. At the cap the gate says `daily-cap` until 00:00 UTC and the retry timer is armed for then. Old log files without the new fields read as 0 (a failure record without `attemptDay` still uses its old failure count once). (2) When the day's 5th attempt fails and none succeeded, `sendAlert` (`packages/backend/src/utils/alert.ts`) logs an ERROR line starting with `ALERT`, and also POSTs to `ALERT_WEBHOOK_URL` (`ALERT_WEBHOOK_FORMAT` = ntfy, slack, discord or json) and/or emails through Resend (`RESEND_API_KEY` + `ALERT_EMAIL_TO`, from `ALERT_EMAIL_FROM`). One alert per UTC day (remembered in the log file) and again on every day the outage lasts; the text says how many days in a row, whether CelesTrak kept the catalog fresh, and how old the catalog is. 10 s timeout, never blocks the cycle, no URL or key in any log line. All settings are optional and listed in `packages/backend/.env.example`. (3) The Space-Track retry timer is armed after every cycle in which Space-Track did not deliver, even when CelesTrak refreshed the cache; only a Space-Track success cancels it (`packages/backend/src/cron/tle-updater.ts`, trigger `retry`). After a restart `resumeSpaceTrackRetry` arms it again from the log. (4) CelesTrak is a fallback OVERLAY: `GROUP=active` in JSON (about 16.7k active satellites, not the full catalog; ids of 100000 and up only exist in JSON). CelesTrak sends only the 17 OMM keys, so a newer record updates only the orbit (omm, epoch, inclination) and what derives from it (period, apogee and perigee from mean motion and eccentricity, regime) of a cached object; type, country, launch date, size and the enrichment facets stay as Space-Track had them. New ids are added with the pipeline's unknown defaults (`packages/backend/src/cache/catalog-overlay.ts`, `mergeNewerOrbit` and `packages/backend/src/utils/orbit-summary.ts`). No 4xx is ever retried. Every CelesTrak download is gated to once per 2 hours per group in `celestrak-attempts.json` (`packages/backend/src/cache/celestrak-attempts.ts`, shared file helpers in `packages/backend/src/cache/state-file.ts`), the visual list included. An overlay result is not written to the history database or the raw archive: history stays Space-Track-only. To clear a CelesTrak wait, delete `celestrak-attempts.json` from the volume.
- Write-failure and volume alerts on `sre/hardening` (D16). If writing the catalog throws (disk full, permissions), the cycle logs ERROR, counts the Space-Track attempt as failed, removes only its own `tle-cache.json.tmp` and `version.json.tmp`, keeps serving the old cache, arms the retry and sends an alert titled `DISK or WRITE problem` with the disk usage line (at most one per UTC day). The data volume sends an alert through the same path at 75% (warn) and 90% (error) used: at most once per UTC day per level, at once when the level gets worse; checked at boot, after each raw archive write and after the 02:00 cycle (`packages/backend/src/utils/volume-alert.ts`). The markers live in the new state file `alert-state.json` in `CACHE_DIR` (`packages/backend/src/cache/alert-state.ts`; `volumeWarnDay`, `volumeErrorDay`, `writeFailureDay`). To make an alert fire again, delete that file. No new environment variables.
- Data-safety hardening on `sre/hardening`. (1) A catalog with 0 objects, or with under 50% of the cached object count, is refused for both Space-Track and CelesTrak (`assessCatalog` in `packages/backend/src/cache/file-cache.ts`, used by `packages/backend/src/cron/tle-updater.ts`; knob `CATALOG_MIN_RATIO`, default 0.5, 0 = only refuse empty). A refused Space-Track answer is an ERROR line, counts as a failure in the attempt log, and falls through to CelesTrak. If CelesTrak is refused too, `tle-cache.json`, `version.json`, the payload cache and the history database are not touched. With no cache any non-empty catalog is taken. (2) When a cycle writes nothing and Space-Track is only waiting out its backoff, one unref'd timer runs the cycle again when the wait ends, not at the next 02:00. (3) DSO snapshot pruning keeps the newest 3 files per object and deletes older ones, only after the manifest points at the new snapshot. Only the newest snapshot is served, so it replaces older values for the same times (OPEN.md). (4) The boot disk report runs last, is not awaited, and gives up after 5 s. (5) An ended DSO mission gets the same 24 h grace in every check, is asked again about weekly (`lastCheckedAt` in `dso/ended.json`), and is counted as `dsoEndedCount` in `GET /health`. Details: `state/SRE_FINDINGS.md`.
- Catalog cue back in the time console on `sre/hardening`: under TRACKING (open console only) a line reads `LOADING DAY…` while a past day is fetched, or `NO CATALOG FOR THIS DATE` in amber when the sky is shown without satellites (also past the forward horizon). The text comes from the pure `catalogCue` in `packages/frontend/src/ui/cockpit/time/time-console.ts`; the line is drawn by `packages/frontend/src/ui/cockpit/time/ConsoleReadouts.tsx`. No animation. The open console grows one line (about 16 px) only while the cue shows; the closed console does not change.
- Space-Track backoff on `sre/hardening`: every Space-Track login is written to `spacetrack-attempts.json` in `CACHE_DIR` (`packages/backend/src/cache/attempt-log.ts`), so a restart cannot reset the wait. After a failure the next login waits 15 min, 30 min, 1 h, 2 h, 4 h, then 6 h; after a success it waits 1 h (the same value as the cron's cache-age guard). While Space-Track is held back, one INFO line says when it may retry, and the stale cache and CelesTrak run as before. A bad or unwritable file only logs a WARN. The 6 h cap is far below a day, so the 02:00 cron is never blocked for a whole day. To clear the wait, delete `spacetrack-attempts.json` from the volume.
- Artemis II retry spam stopped on `sre/hardening`: when Horizons answers "no ephemeris prior to / after", the worker clamps the window at both ends and retries (3 requests at most; `packages/backend/src/dso/providers/horizons.ts`). If the data ended more than a day ago the object is saved as ended in `dso/ended.json` under `CACHE_DIR` (`packages/backend/src/dso/worker/ended-state.ts`). From then on it asks again only about once a week (see the data-safety item above), logs one INFO line per boot, and keeps serving the stored ephemeris unchanged. In plain words for Artemis II: after its first cycle following this deploy it gets one final continuous snapshot (data from Horizons' first to last available time, 10-minute steps, trimmed 10 minutes at each end as a safety margin for the TDB/UTC difference). Then it is marked ended and re-checked weekly, so updated values replace the old ones. To retry a finished mission: set `DSO_RETRY_ENDED=1` and restart (one try per object per boot; live data clears the flag by itself), or delete the object's entry from `ended.json`. Unset the variable afterwards.
- Smaller downloads on `sre/hardening`: `GET /api/tle/all` is served as brotli when the browser allows it, else gzip as before. `packages/backend/src/cache/tle-payload-cache.ts` builds the gzip copy at once and the brotli copy afterwards on the thread pool (quality 10, about 35 s measured on Railway, about +50 MB RAM, about 23% smaller than gzip; the size figure was measured on fake data). ## Facts an agent must know

- `ER_KM = 6371` is the scene and wire length unit. It never changes.
  The Earth's shape is WGS84 and lives only in `earth.ts`. They are different things.
- Latitude and altitude on the ellipsoid need TEME or ECEF vectors.
  Scene vectors are Y-up. Convert with `sceneToSource` in `packages/frontend/src/engine/scene/frames.ts` first.
- Two propagation engines are in use and they differ slightly.
  The Rust/WASM crate uses WGS84 gravity. `satellite.js` is hard-coded WGS72.
  Gap: LEO median 37 m now, about 250 m at +7 days. The owner accepted this.
- The rendered globe is still a unit sphere. Error is under 0.3 percent, under 2 pixels. Takram replaces it later.
- The frontend has one query system, the Analytic IR. `packages/frontend/src/query/` holds only its live data source and the installed launch/org vocabulary.
  The older keyword engine (parser, executor, aliases) was removed with the old overlay.
- `packages/wasm-sgp4/pkg/` is committed and was not rebuilt after the constant rename. Output is identical.
